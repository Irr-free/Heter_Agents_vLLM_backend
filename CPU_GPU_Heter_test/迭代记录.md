### 1. 修复 torch.compile AOT 编译失败（架构重构）

#### 问题根因
- `forward()` 中直接调用 `_cpu_decode_forward()`（带 `@torch.compiler.disable()`），导致 `torch._dynamo.exc.Unsupported: Skip inlining`
- `forward()` 中调用 `torch.cuda.is_current_stream_capturing()`（返回 bool），在 `fullgraph=True` 模式下不被允许
- `output.copy_(output_cpu.to(query.device))` 在 dummy run 期间触发 `InductorError: LoweringException: AssertionError`

#### 解决方案
将 CPU decode 路径**完全移出 `forward()` 的可编译区域**，放到已存在的 custom op `unified_attention_with_output` 内部执行：

| 修改项 | 说明 |
|--------|------|
| `forward()` 简化 | 移除 `is_pure_decode` 分支，恢复为统一调用 `unified_attention_with_output`；仅保留 `num_prefill_tokens > 0` 时的 async D2H 触发 |
| `unified_attention_with_output` 内嵌 CPU 路径 | 在 custom op 内部判断 `num_prefill_tokens == 0 && not is_cudagraph_capturing() && cpu_kv_cache is not None`，满足条件则走 CPU decode 路径（D2H 同步 → KV 搬运 → CPU Attention → 结果搬回 GPU） |
| `_cpu_paged_attention_fallback` 注册为 custom op | 使用 `direct_register_custom_op(..., dispatch_key="CPU")` 注册，避免 CPU tensor 输入时 dispatch 失败 |
| 移除 `@torch.compiler.disable()` | `_cpu_decode_forward()` 不再被 `forward()` 调用，装饰器自然失效 |

### 2. 修复 CPU Attention Fallback 数值 Bug

| Bug | 修复方式 |

| `RuntimeError: tensor size mismatch at dim 0` (44 vs 32) | `torch.matmul(q_seq, k_seq.transpose(1,2))` 的 batch 维度不匹配（`num_query_tokens` vs `num_heads`）。改为 `torch.einsum('qhd,hkd->qhk', q_seq, k_seq)` 和 `torch.einsum('qhk,hkd->qhd', scores, v_seq)` |

## 关键设计决策（本迭代更新）

1. **Custom Op 作为 CPU 路径的"避风港"**：`unified_attention_with_output` 本身就是 custom op（torch.compile 不可见），将 CPU 路径内嵌其中，既避免了 graph break，又无需新增 op 接口。
2. **`is_cudagraph_capturing()` 而非 `torch.cuda.is_current_stream_capturing()`**：后者只在 CUDA stream 真正 capture 时返回 True，而 vLLM 的 profile/warmup 阶段全局标记已启用但 stream 尚未 capture。使用前者可避免 dummy run 误入 CPU 路径。
3. **`dispatch_key="CPU"`**：Python fallback 操作的全是 CPU tensor，必须注册到 CPU dispatch key，否则 PyTorch 会根据输入设备查找对应 backend 实现并报 `NotImplementedError`。

### 1. 修复 `init_cpu_kv_cache()` block 数不匹配

**根因**：vLLM V1 的初始化流程中，`bind_kv_cache()` 会被调用两次：
1. 第一次：profile run 前，绑定的是 **dummy/profiling KV cache**（很小，如 8 个 block）
2. 第二次：profile run cleanup 后，绑定的是 **真正的 KV cache**（如 13,000+ 个 block）

`init_cpu_kv_cache()` 中原有的 `if self.cpu_kv_cache is not None: return` guard 导致第二次调用时直接跳过，CPU cache 始终保持 profile 期间的小尺寸。

**修复**：移除简单 guard，改为检查 shape 是否匹配。若 `num_blocks` 或 `block_size` 变化，则释放旧 cache 并重新分配：
```python
if self.cpu_kv_cache is not None:
    if (self.cpu_kv_cache.shape[1] == num_blocks and
            self.cpu_kv_cache.shape[3] == block_size):
        return
    self.cpu_kv_cache = None
    self._d2h_stream = None
```

## 已知限制与后续优化方向

1. **性能极低**：Python fallback 的 decode 吞吐仅 ~0.5 tokens/s（32 层 × CPU matmul）。需要编译/注册真正的 C++ CPU kernel（`cpu_attention_with_kv_cache` / `cpu_attn_reshape_and_cache`）。
2. **CUDA Graph 兼容**：当前 pure decode batch 在 `unified_attention_with_output` custom op 内部走 CPU 路径，完全绕过了 CUDA graph。这导致 decode 无法享受 CUDA graph 的启动加速。
3. **Mixed Batch**：当前 Prefill+Decode 混合 batch 统一走 GPU 路径，未做拆分。
4. **CPU KV Cache 内存占用**：按 GPU KV cache 同等大小分配 CPU pinned memory，对于大模型可能占用数十 GB 主存。
